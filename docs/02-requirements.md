## 1. Контекст

Банк предоставляет клиентам услугу хранения ценностей и операции с драгоценными металлами. Процесс включает открытие договора и счёта, внесение и выдачу ценностей, начисление комиссии, формирование выписки и закрытие договора.

В процессе участвуют фронт-офис, бэк-офис, касса, АБС и процессинг. Часть операций выполняется асинхронно, поэтому критичны статусы, повторные запросы и сверка остатков.

## 2. Цели и метрики успеха

| ID | Цель | Метрика |
|---|---|---|
| G-01 | Сократить время обслуживания клиента | Среднее время открытия договора и счёта — не более 15 минут |
| G-02 | Убрать ручные сверки на happy path | Доля операций без ручного разбора — не менее 95% |
| G-03 | Сделать ошибки понятными | 100% ошибок имеют код, сообщение и рекомендуемое действие |
| G-04 | Сократить дефекты на UAT | Снижение количества дефектов category A/B на 25% |
| G-05 | Ускорить выпуск изменений | Согласование требований — не более 5 рабочих дней на типовое изменение |

## 3. Scope

### Входит в scope

- открытие, активация, приостановка и закрытие договора хранения;
- открытие и закрытие счёта;
- внесение и выдача ценностей / металла;
- начисление комиссии;
- формирование выписки;
- интеграция фронт-офиса, АБС, кассы и процессинга;
- сверка остатков и обработка расхождений;
- роли и права доступа;
- UAT и передача в поддержку.

### Не входит в scope

- кредитные и депозитные продукты;
- инвестиционные операции и биржевые котировки;
- бухгалтерская отчётность банка;
- миграция исторических данных за пределами согласованного объёма;
- мобильное приложение клиента (использует существующий фронт).

## 6. Функциональные требования

### 6.1. Договор

| ID | Требование | Приоритет | Критерий приёмки |
|---|---|---|---|
| FR-01 | Создать договор в статусе `DRAFT` | Must | Возвращается `contractId`, статус `DRAFT`, дата создания |
| FR-02 | Активировать договор после открытия счёта и подтверждения остатка | Must | Переход `DRAFT → OPEN → ACTIVE`; при ошибке статус не меняется |
| FR-03 | Приостановить договор при аресте или блокировке | Must | Переход `ACTIVE → SUSPENDED`; операции приёма/выдачи недоступны |
| FR-04 | Возобновить договор после снятия ограничений | Must | Переход `SUSPENDED → ACTIVE`; доступность операций восстановлена |
| FR-05 | Закрыть договор | Must | Переход `ACTIVE → CLOSING → CLOSED` только при выполнении guard-условий |
| FR-06 | Отменить договор до активации | Should | Переход `DRAFT/OPEN → CANCELLED`; счёт не создаётся или закрывается |

### 6.2. Счёт

| ID | Требование | Приоритет | Критерий приёмки |
|---|---|---|---|
| FR-07 | Открыть счёт по договору | Must | Возвращается `accountId`, маска номера, валюта, статус `OPEN` |
| FR-08 | Показать баланс и статус счёта | Must | Возвращается баланс, валюта, дата обновления |
| FR-09 | Заблокировать / разблокировать счёт | Must | Статус меняется, операция фиксируется в журнале аудита |
| FR-10 | Закрыть счёт | Must | Закрытие только при нулевом остатке и отсутствии активных ордеров |

### 6.3. Операции с ценностями

| ID | Требование | Приоритет | Критерий приёмки |
|---|---|---|---|
| FR-11 | Создать операцию внесения | Must | Возвращается `operationId`, статус `PENDING`, идемпотентность по ключу |
| FR-12 | Создать операцию выдачи | Must | Проверяется достаточность остатка; при недостатке — `409 Conflict` |
| FR-13 | Получить статус операции | Must | Возвращается `PENDING / CONFIRMED / REJECTED / CANCELLED` |
| FR-14 | Обработать повторный запрос с тем же `Idempotency-Key` | Must | Возвращается тот же результат, дубль не создаётся |
| FR-15 | Обработать таймаут и повтор | Must | Retry не приводит к двойному списанию/зачислению |
| FR-16 | Создать инцидент при расхождении остатков | Must | Инцидент содержит `operationId`, причину, статус, владельца |

### 6.4. Комиссии и выписки

| ID | Требование | Приоритет | Критерий приёмки |
|---|---|---|---|
| FR-17 | Начислить комиссию за период | Must | Возвращается `commissionId`, сумма, валюта, статус |
| FR-18 | Сформировать выписку | Should | Возвращается `statementId`, период, формат, ссылка на файл |
| FR-19 | Показать историю операций по договору | Should | Список с пагинацией, фильтрами по дате и типу |

### 6.5. Доступ и аудит

| ID | Требование | Приоритет | Критерий приёмки |
|---|---|---|---|
| FR-20 | Ограничить действия по ролям | Must | Роль не может выполнить операцию вне своей матрицы прав |
| FR-21 | Логировать изменения статусов | Must | В журнале есть кто, когда, что и с какого статуса изменил |
| FR-22 | Показывать пользователю понятную ошибку | Must | Код, сообщение, рекомендация, `X-Request-ID` |

## 8. Бизнес-правила

| ID | Правило |
|---|---|
| RULE-01 | Валюта счёта должна совпадать с валютой договора |
| RULE-02 | Маска номера счёта зависит от типа клиента и требований ИБ |
| RULE-03 | Сумма операции должна быть больше нуля |
| RULE-04 | Вес металла указывается с точностью до 6 знаков |
| RULE-05 | Комиссия рассчитывается за календарный период и округляется по правилам банка |
| RULE-06 | Закрытие договора запрещено при остатке > 0 |
| RULE-07 | Закрытие договора запрещено при активном ордере |
| RULE-08 | Закрытие договора запрещено при аресте или блокировке |
| RULE-09 | Повторный запрос с тем же `Idempotency-Key` возвращает исходный результат |
| RULE-10 | При расхождении остатков операция не считается успешной до ручного разбора |
| RULE-11 | Все денежные суммы хранятся в decimal, не в float |
| RULE-12 | Даты передаются в ISO 8601, время — в UTC |

## 9. Требования к данным

- Суммы — `decimal(18,2)`, вес — `decimal(18,6)`.
- Валюты — ISO 4217, страны — ISO 3166-1 alpha-2.
- Идентификаторы — UUID; внешние идентификаторы — строка с ограничением длины.
- Обязательные поля валидируются на API и в БД.
- Персональные данные не логируются и не передаются в аналитику в открытом виде.
- Для каждой сущности определены владелец, жизненный цикл и правила архивирования.
- Расхождения остатков фиксируются как инцидент с историей изменений.

## 11. Допущения и ограничения

- Процессинг поддерживает идемпотентность на своей стороне.
- Кассовая система умеет подтверждать фактический приём/выдачу.
- Исторические данные мигрируются отдельным проектом.
- Бизнес-правила по комиссиям согласуются с финансовым блоком.
- Изменения в АБС требуют отдельного релизного окна.

## 13. Критерии готовности требований (DoR)

- Описан бизнес-контекст и цель.
- Определены стейкхолдеры и владелец решения.
- Есть функциональные и нефункциональные требования.
- Описаны исключения и ошибки.
- Определены критерии приёмки.
- Согласованы зависимости и ограничения.
- Есть оценка влияния на данные, интеграции и безопасность.

## 14. Критерии готовности решения (DoD)

- Реализация соответствует требованиям и контрактам.
- Пройдены unit, integration и UAT-проверки.
- Обновлены документация, runbook и инструкции.
- Настроены метрики, логи и алерты.
- Проведена демонстрация бизнесу.
- Получен sign-off и решение передано в поддержку.
