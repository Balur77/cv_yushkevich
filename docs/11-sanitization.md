# Обезличивание и публикация портфолио

> Как из рабочих схем и документов получить безопасное портфолио, не нарушив NDA.

---

## 1. Главный принцип

**Не публикуйте оригиналы.** Даже если «кажется, что ничего секретного нет», в схеме почти всегда есть:

- названия внутренних систем;
- номера счетов и договоров;
- API-пути и имена полей;
- статусы и коды;
- бизнес-правила и лимиты;
- имена сотрудников;
- организационная структура.

Безопаснее **перерисовать схему с нуля** по мотивам кейса, чем замазывать текст на скриншоте.

## 2. Что было заменено в этом репозитории

| Было (рабочий артефакт) | Стало (портфолио) |
|---|---|
| Название банка / клиента | «Крупный банк», без имени |
| Названия внутренних систем | «АБС», «Кассовая система», «Фронт-офис», «Процессинг» |
| Внутренние модули и сервисы | Обобщённые компоненты |
| Реальные API-пути | `/contracts`, `/accounts`, `/operations` |
| Имена полей БД | `contractId`, `accountId`, `operationId` |
| Внутренние статусы | `DRAFT`, `ACTIVE`, `CLOSED`, `MANUAL_REVIEW` |
| Номера счетов | Маска `**** 1234` |
| Идентификаторы и GUID | UUID-примеры |
| Названия оргструктур | «Фронт-офис», «Бэк-офис», «Касса» |
| Бизнес-правила и лимиты | Иллюстративные правила |
| Скриншоты интерфейса | Перерисованные схемы |
| Имена и контакты | Удалены |
| Метрики проекта | Оценочные, обезличенные |

## 3. Чек-лист перед публикацией

### Текст и документы

- [ ] Нет названия работодателя и клиента.
- [ ] Нет названий внутренних систем, модулей, сервисов.
- [ ] Нет реальных API-путей и имён полей.
- [ ] Нет номеров счетов, договоров, карт, телефонов.
- [ ] Нет ФИО клиентов и сотрудников.
- [ ] Нет внутренних кодов, статусов, лимитов и тарифов.
- [ ] Нет ссылок на внутренние Confluence/Jira.
- [ ] Нет фрагментов переписок и ТЗ.
- [ ] Нет коммерческих метрик, которые нельзя раскрывать.
- [ ] Нет упоминаний подрядчиков и интеграторов.

### Диаграммы

- [ ] Схема перерисована, а не отрендерена из рабочей системы.
- [ ] Подписи обобщены.
- [ ] Нет логотипов и брендов.
- [ ] Нет реальных идентификаторов.
- [ ] Нет скрытых слоёв и метаданных.
- [ ] Проверен SVG/PNG на наличие текста (иногда текст остаётся в `<text>`).
- [ ] Проверены EXIF/метаданные изображений.

### Код и конфиги

- [ ] Нет токенов, паролей, ключей.
- [ ] Нет внутренних URL и IP.
- [ ] Нет `.env` с реальными значениями.
- [ ] Нет тестовых данных с ПДн.
- [ ] Нет закомментированных секретов.
- [ ] Проверена история git (если репозиторий уже существовал).

### Метаданные

- [ ] В PDF удалены автор, организация, комментарии.
- [ ] В DOCX удалены свойства и скрытый текст.
- [ ] В изображениях удалены GPS и EXIF.
- [ ] В SVG удалены `title`, `desc`, `metadata` с внутренними названиями.

## 4. Автоматическая проверка

В репозитории есть скрипт:

```powershell
python scripts/scan_sensitive.py
```

Он ищет:

- названия систем и банка;
- реальные контакты;
- подозрительные пути и идентификаторы;
- служебные файлы.

Скрипт — вспомогательный. Он не заменяет ручную проверку.

## 5. Проверка PDF

```powershell
# Посмотреть метаданные
python -c "import pymupdf; d=pymupdf.open('resume.pdf'); print(d.metadata)"

# Удалить метаданные (пример)
python -c "import pymupdf; d=pymupdf.open('resume.pdf'); d.set_metadata({}); d.save('resume_clean.pdf')"
```

Перед публикацией проверьте, что в PDF нет:

- имени организации;
- внутренних комментариев;
- скрытых слоёв;
- ссылок на внутренние ресурсы.

## 6. Проверка изображений

```powershell
python -c "from PIL import Image; im=Image.open('diagram.png'); print(im.info); print(im.getexif())"
```

Для SVG откройте файл текстом и проверьте:

- `<title>`;
- `<desc>`;
- `<metadata>`;
- комментарии `<!-- -->`;
- имена слоёв.

## 7. Если очень нужно показать «настоящую» схему

Не показывайте. Вместо этого:

1. Опишите кейс текстом.
2. Нарисуйте обобщённую схему.
3. Покажите, как вы мыслили, а не как выглядела система.
4. На интервью расскажите детали устно, без записи.

## 8. Публикация

```powershell
cd portfolio
git init
git add .
git commit -m "Portfolio: anonymized system analysis artifacts"
git branch -M main
git remote add origin https://github.com/<username>/<repo>.git
git push -u origin main
```

Перед `git push`:

- [ ] `python scripts/scan_sensitive.py` — без находок.
- [ ] Проверить `git status` — нет лишних файлов.
- [ ] Проверить `.gitignore`.
- [ ] Проверить, что в репозитории нет оригиналов из `D:\CV`.
- [ ] Проверить историю, если репозиторий не новый.

## 10. Если сомневаетесь

Задайте себе три вопроса:

1. Могу ли я показать это бывшему работодателю без вопросов?
2. Не раскрывает ли это архитектуру или бизнес-правила?
3. Не содержит ли это данных, которые нельзя публиковать?

Если хотя бы один ответ «нет» или «не уверен» — не публикуйте.
