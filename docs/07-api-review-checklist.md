# Чек-лист ревью API-контракта

> Используется до начала разработки и на ревью изменений. 40+ проверок.
> Связанные артефакты: [OpenAPI](03-api-specification.yaml), [требования](02-requirements.md), [UAT](05-test-scenarios.md).

---

## 1. Контракт и ресурсы

- [ ] Ресурсы названы существительными, в единственном или множественном числе последовательно.
- [ ] Используются корректные HTTP-методы (`GET` без побочных эффектов, `POST` для создания).
- [ ] Коды ответов соответствуют смыслу: `200`, `201`, `202`, `204`, `400`, `401`, `403`, `404`, `409`, `422`, `429`, `500`, `503`.
- [ ] Для создания возвращается `Location`.
- [ ] Для асинхронной операции возвращается `202 Accepted` и ссылка на статус.
- [ ] Пагинация описана (`page`, `pageSize`, `total`).
- [ ] Фильтры и сортировка описаны и ограничены.
- [ ] Нет «глаголов» в путях, кроме действий, которые действительно не являются CRUD (`/close`, `/activate`).
- [ ] Версионирование API явное (`/v1`).
- [ ] Обратная совместимость в рамках мажорной версии соблюдена.

## 2. Схемы и типы

- [ ] У всех полей указан тип, формат и ограничения.
- [ ] `required` соответствует реальным обязательным полям.
- [ ] Для сумм используется decimal, не float.
- [ ] Даты — ISO 8601, время — UTC.
- [ ] Валюты — ISO 4217, страны — ISO 3166-1.
- [ ] Идентификаторы — UUID или явно описанный формат.
- [ ] Enum-значения полные и не противоречат статусной модели.
- [ ] `nullable` указан только там, где это действительно возможно.
- [ ] Нет «магических» строк без справочника.
- [ ] Примеры (`examples`) заполнены и валидны.

## 3. Ошибки

- [ ] Единый формат ошибок (Problem Details).
- [ ] У каждой ошибки есть машинный `code`.
- [ ] Есть человекочитаемое `message`.
- [ ] Есть `details` для полевых ошибок.
- [ ] Есть `requestId` для поддержки.
- [ ] Ошибки не раскрывают внутренние детали и ПДн.
- [ ] `409` используется для конфликта состояния, а не для любой ошибки.
- [ ] `422` используется для бизнес-валидации.
- [ ] Для `429` есть `Retry-After`.
- [ ] Для `503` описано поведение клиента.

## 4. Идемпотентность и повтор

- [ ] Все команды создания/изменения поддерживают `Idempotency-Key`.
- [ ] Повтор с тем же ключом и тем же payload возвращает исходный результат.
- [ ] Повтор с тем же ключом и другим payload возвращает конфликт.
- [ ] Срок жизни ключа описан.
- [ ] Retry не приводит к двойному списанию/зачислению.
- [ ] Таймауты описаны для каждого внешнего вызова.
- [ ] Есть стратегия backoff и максимум попыток.
- [ ] Есть circuit breaker или предохранитель.
- [ ] Для асинхронных операций описан polling/webhook.
- [ ] Описан сценарий «ответ потерян, операция выполнена».

## 5. Безопасность

- [ ] Аутентификация описана (OAuth2 / JWT / mTLS).
- [ ] Авторизация проверяется на уровне операции, а не только UI.
- [ ] Нет ПДн в URL и логах.
- [ ] Секреты не передаются в query string.
- [ ] Ограничен размер payload.
- [ ] Есть rate limiting.
- [ ] Ошибки не раскрывают существование чужих объектов.
- [ ] Аудит действий описан.
- [ ] Для межсистемных вызовов используется mTLS или подпись.
- [ ] Проверены требования ИБ и комплаенса.

## 6. Наблюдаемость

- [ ] `X-Request-ID` принимается и возвращается.
- [ ] Логи содержат корреляцию, но не содержат ПДн.
- [ ] Метрики: latency, error rate, RPS, retry count.
- [ ] Алерты настроены на ошибки и деградацию.
- [ ] Трассировка связывает фронт, шину и бэкенд.
- [ ] Для инцидентов есть runbook.
- [ ] Есть health / readiness / liveness.

## 7. Данные и совместимость

- [ ] Маппинг source → target описан.
- [ ] Валидации согласованы с БД.
- [ ] Уникальность внешних идентификаторов обеспечена.
- [ ] Миграции не ломают старые контракты.
- [ ] Новые поля не обязательны для старых клиентов.
- [ ] Удаление полей — только через deprecation.
- [ ] Есть стратегия архивирования и retention.
- [ ] Тестовые данные не содержат реальных ПДн.

## 8. Документация и поддержка

- [ ] У каждого метода есть `summary`, `description`, `operationId`.
- [ ] Описаны все ответы, включая ошибки.
- [ ] Есть примеры запросов и ответов.
- [ ] Есть Postman-коллекция или mock.
- [ ] Описаны ограничения и лимиты.
- [ ] Есть changelog.
- [ ] Поддержка знает, как диагностировать ошибку по `requestId`.
- [ ] Контракт проверен линтером/валидатором.

---

## Как использовать

1. Пройти чек-лист на этапе проектирования.
2. Зафиксировать замечания в Jira.
3. Повторить на ревью перед релизом.
4. Приложить результат к change request.
